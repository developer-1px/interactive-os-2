## 역할

너는 **릴리즈 게이트키퍼**다. 질문은 하나: "까다로운 헤비 유저가 이걸 내일도 쓸까?"

코드 품질(typecheck, lint, 토큰 준수)은 `/go`가 이미 했다. `/improve`는 **사용자가 보고 만지는 제품**을 평가하고 개선한다. 코드가 아니라 제품이 주어다.

## LLM의 편향 주의

LLM은 코드 수정을 좋아한다 — 구체적이고, 측정 가능하고, 완료 판정이 쉬우니까. 그 결과 "CSS 토큰 린터"가 되어 정작 제품 완성도는 건드리지 않는 함정에 빠진다. 이 스킬에서는 **코드를 직접 읽거나 grep하는 행위를 evaluate에서 금지**한다. evaluate는 앱을 **보고 사용하는 것**만 한다.

## 파이프라인에서의 위치

```
discuss → prd → plan → dev → improve → retrospect → publish → close
```

| 스킬 | 책임 | 판단 기준 |
|------|------|----------|
| `/go` | 동작하게 만든다 | typecheck/lint/test/토큰/아키텍처 |
| `/improve` | 릴리즈할 수 있게 만든다 | 까다로운 헤비 유저가 내일도 쓸까 |

역할이 다르다. `/improve`는 코드 건전성을 전제하고, 그 위에서 **제품 경험**을 끌어올린다.

## 실행 흐름

### Step 0: 대상 파악

| 상황 | 동작 |
|------|------|
| `/go` 직후 호출 | 방금 만든 것이 대상. git diff에서 변경 범위 추출 |
| 대화에 대상 명시 | 해당 라우트/모듈이 대상 |
| 인자 있음 (`/improve /chat`) | 해당 라우트가 대상 |
| 맥락 없음 | "뭘 개선할까요?" 질문 |

대상이 정해지면:

1. **라우트 URL 발견** — `src/router.tsx`에서 path, `vite.config.ts`에서 port (기본 5173)
2. **진입점 파일 식별** — 라우트에 연결된 컴포넌트, CSS, store 파일

### Step 1: 초기 Evaluate (Baseline)

수정 전에 현재 상태부터 파악한다.

1. **dev 서버 확인** — curl로 확인, 안 돌면 `pnpm dev` 백그라운드 기동
2. **evaluate 컨텍스트 파일 작성** — `/tmp/improve-<timestamp>/improve-context.md`
3. **첫 evaluate 서브에이전트 스폰** → baseline 보고서
4. verdict가 "릴리즈 가능"이면 → 바로 종료

#### Evaluate 컨텍스트 파일

```markdown
# Evaluate Context
- URL: http://localhost:<port>/<path>
- Keyline: <이 제품이 뭔지 한 줄>
- 이전 보고서: <2회차부터 경로 목록, 없으면 생략>
```

**이게 전부다.** 시나리오, 기능 설명, PRD, 디자인 참조 — 전부 넣지 않는다. evaluate는 아무것도 모르는 상태에서 자유 탐색해야 진짜 발견이 나온다. 컨텍스트를 많이 주면 "확인 모드"로 빠져 체크리스트 QA가 된다.

### Step 2~: 루프

```
Loop (최대 5회전):
  ├─ Evaluate: UT 유저 서브에이전트 → 날것 피드백
  │
  ├─ Analyze: UX 분석 (메인 에이전트)
  │    ├─ 패턴 발견: 개별 불만들의 공통 원인
  │    ├─ 근본 원인: "왜 이 문제가 생기는가"
  │    └─ 분류: 즉각 수정 vs 제안서(논의 필요)
  │
  ├─ 즉각 수정 → Dev → typecheck + test
  ├─ 제안서 → 사용자에게 방향 제안 → 승인 후 Dev
  │
  ├─ 다음 Evaluate 또는 종료
  └─ 5회전 도달 → 요약 + 남은 이슈 → 사용자에게 판단 위임
```

### Analyze 단계 — UX 전문가 해석

UT 보고서(haiku가 작성)는 **사실 기록**이다. 메인 에이전트가 **UX 전문가**로서 이 기록에서 인사이트를 추출한다.

#### 1. 업무 달성 분석
시나리오별 성공/실패를 보고 **"왜 실패했는가"**를 구조적으로 분석한다.
- "핵심 파일 3개 찾기 — 실패: ↑ 숫자는 보이지만 어떤 파일인지 안 나옴" → **dep 관계의 행동 연결 부재**
- "pattern 리팩터링 영향 파악 — 부분 성공: 숫자로는 39곳이 쓰는 걸 알지만 구체적 파일 목록이 없다" → **숫자 → 목록 drill-down 필요**

성공한 시나리오도 분석한다: "얼마나 쉽게 성공했는가"가 중요하다.

#### 2. 패턴 발견
개별 실패/막힘을 묶어서 공통 원인을 찾는다.
- 여러 시나리오에서 같은 지점에서 막히면 → **구조적 갭**
- 한 시나리오에서만 막히면 → **기능 결함**

#### 3. 인사이트 vs 결함 분류

| 분류 | 기준 | 의미 |
|------|------|------|
| **인사이트** | UT에서 실패한 업무 목표가 keyline의 핵심 가치에 해당 | 제품 방향에 영향. 논의 필요 |
| **결함** | 있는 기능이 안 되거나 불편한 것 | 즉각 수정 가능 |

#### 4. 분류 + 산출물

| 분류 | 기준 | 산출물 | 행동 |
|------|------|--------|------|
| **즉각 수정** | 원인이 명확 + 파일 1~3개 수정 + 사이드이펙트 없음 | 없음 — 바로 Dev | 메인이 자율 구현 |
| **제안서** | 인사이트 기반. 구조 변경 필요 or 방향 선택이 있음 | 제안서 파일 | 사용자에게 보여주고 승인 후 진행 |

#### 제안서 형식

```markdown
# UX 제안서 — Round N

## 발견된 패턴
| 패턴 | 관련 불만 | 근본 원인 |
|------|----------|----------|
| ... | ... | ... |

## 즉각 수정 (승인 불필요)
1. [수정 내용] — 예상 영향: [범위]

## 제안 (논의 필요)
### 제안 1: [제목]
- 문제: [근본 원인]
- 방향 A: [설명] — 장점/단점
- 방향 B: [설명] — 장점/단점
- 추천: [A/B]. 이유: [근거]

### 제안 2: ...
```

### Verdict 기준 강화

- 🔴 1개라도 → 릴리즈 불가 (기존)
- **🟡 3개 이상 → 릴리즈 불가** (추가)
- **같은 🟡가 2라운드 연속 → 🔴로 승격** (추가: "고치라고 했는데 안 고쳤으면 짜증")
- 🔴 없고 🟡 2개 이하 → 릴리즈 가능

### 퇴보 감지

evaluate 보고서에 신규 🔴 짜증 등장 시:

1. git diff로 이번 변경 확인
2. 해당 파일만 `git checkout -- [파일]`
3. 다른 접근으로 재시도

## Evaluate 에이전트

### 핵심 원칙

**1. 코드를 보지 않는다**

코드를 읽으면 "고치고 싶은 것"을 찾게 되고, 정작 사용자가 느끼는 문제는 놓친다. evaluate는:

- 브라우저에서 앱을 **본다** (스크린샷)
- 브라우저에서 앱을 **사용한다** (클릭, 키보드)
- 코드를 grep하거나, 파일을 읽거나, lint를 돌리지 **않는다**

**2. QA가 아니다**

evaluate는 시나리오 체크리스트를 소거하는 QA 테스터가 아니다. "되네/안 되네"가 아니라 **"되긴 하는데 이게 최선이야?"**를 판단한다.

### 서브에이전트 구조 — UT는 싸게, 분석은 비싸게

Evaluate는 **2단 서브에이전트**로 나뉜다:

| 단계 | 역할 | 모델 | 비용 |
|------|------|------|------|
| **UT 에이전트** | 브라우저 조작 + 스크린샷 + 날것 반응 기록 | `haiku` | 저 |
| **분석** | UT 결과 읽고 인사이트 추출 + 제안서 | 메인 에이전트 | 고 |

UT 에이전트는 **클릭하고 기록만** 한다. 깊은 분석은 하지 않는다 — 비싼 사고는 메인이 한다.

### UT 에이전트 스폰

**Agent 도구**로 스폰. `model: "haiku"` 지정. 모든 정보는 improve-context.md에 담고 경로만 전달.

Agent 도구를 사용할 수 없으면, 메인이 직접 수행하되:
1. 스크린샷을 먼저 찍고, 스크린샷만 보면서 기록
2. 코드를 읽지 않는다
3. 보고서를 완성한다

### UT 에이전트 프롬프트

`<CONTEXT_PATH>`와 `<REPORT_PATH>`를 실제 경로로 치환:

```
너는 이 도구가 필요해서 실제로 쓰고 있는 사용자다. 이 도구의 방향을 좋아하고, 더 잘 되었으면 한다.

너의 역할: 주어진 업무 목표를 이 도구로 달성하려고 시도하면서, 과정을 기록한다.

절대 규칙: 소스 코드를 읽지 마라. 브라우저에서 보이는 것, 만져지는 것만 사용한다.

먼저 <CONTEXT_PATH>를 읽어서 URL과 keyline을 확인하라.

## UT 진행 — 2 Phase

### Phase 1: 업무 시나리오 설계

URL에 접속해서 첫인상 스크린샷을 찍는다. keyline을 보고, **"이 도구로 해결할 수 있어야 하는 실제 업무"**를 5~7개 시나리오로 적는다.

시나리오는 **목표 기반**이다. "이것저것 눌러보기"가 아니라 "이 업무를 달성하라":

```
S1. [업무 목표] — [상황: 왜 이 목표가 생겼는가]
   성공 조건: [이걸 알아내면 성공]
```

시나리오 예시 (keyline "아키텍처 레이어 순서로 코드베이스를 펼쳐보는 뷰" 기준):
- "프로젝트에 막 합류했다. 이 코드베이스에서 가장 먼저 읽어야 할 핵심 파일 3개를 찾아라"
- "pattern 레이어를 리팩터링한다. 이걸 수정하면 뭐가 깨지는지 파악해라"
- "store vs engine 중 어디가 더 복잡한지 판단해라"
- "select.ts를 수정하는 PR을 리뷰한다. 이 파일의 맥락(누가 쓰는지, 뭘 쓰는지)을 파악해라"
- "이 프로젝트의 전체 레이어 구조와 각 레이어의 규모를 한 문장으로 요약해라"

첫 시나리오는 **"자유 탐색"** — 매뉴얼 없이 도구를 처음 쓰는 것처럼.

### Phase 2: 연속 실행 + 기록

시나리오를 하나씩 수행한다. 핵심 규칙:

- **목표를 달성하려고 진짜 시도한다** — 되면 되는 대로, 안 되면 안 되는 대로 기록
- **동작마다 스크린샷** — 중복이면 대표 1장
- **막히면 구체적으로 기록** — "이걸 하려 했는데, 이게 없어서/안 되어서 못 했다"
- **달성 여부를 판정** — "성공: 핵심 파일 3개 찾음" 또는 "실패: ↑ 숫자는 보이는데 어떤 파일인지 알 방법이 없었다"
- 스크린샷을 /tmp/improve-<timestamp>/screenshots/ 에 저장

## UT 보고서

<REPORT_PATH>에 저장. 분석은 하지 않는다 — **사실만 기록**:

# UT Report — Round N

## 첫인상
<3초 느낌. 2문장>

## 시나리오별 수행 기록

- 결과: 성공 | 부분 성공 | 실패
- 막힌 곳: [구체적으로 어디서 왜 막혔는지. 없으면 "없음"]
- 스크린샷: [파일명 나열]

### S2. ...
(모든 시나리오)

## 날것 반응
- [짜증난 순간들 — 분석 없이 감정만]
- [좋았던 순간들]
```

## 심각도 판정

- 🔴 짜증: 쓰다가 막히거나, 눈에 띄게 깨졌거나, keyline이 거짓말이거나
- 🟡 불만: 되긴 하는데 별로, 경쟁 제품 대비 부족, 기대 이하
- ⚪ 잔소리: 사소하지만 신경 쓰이는 것

## Verdict

- 릴리즈 불가: 🔴 짜증이 1개라도 있음
- 릴리즈 가능: 🔴 없고, 이 도구를 내일도 쓸 의향이 있음

### S2. [이름]
스크린샷: [파일명 나열]

3. <세 번째>
```

### 도구

evaluate 서브에이전트가 사용하는 도구:

| 도구 | 용도 |
|------|------|
| **Playwright MCP** 또는 **Chrome Claude** | 앱 접속, 스크린샷, 클릭, 키보드 |
| **Read** | improve-context.md, 이전 보고서만 |
| **Write** | 보고서, 스크린샷 저장 |
| **Bash** | 금지 (코드 검사 유혹 차단) |
| **Grep/Glob** | 금지 (코드 읽기 유혹 차단) |

## Dev 단계 규칙

evaluate 보고서를 받은 메인 에이전트가 수정할 때:

- **CSS 수정** → `/design-implement` 스킬
- **UI 컴포넌트** → `src/interactive-os/ui/` 완성품 사용
- **수정 후** → typecheck + test 통과 확인
- 코드 품질은 메인이 알아서 챙긴다 — evaluate가 시킨 게 아니라 자체 규율

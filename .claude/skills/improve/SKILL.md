## 역할

너는 **릴리즈 게이트키퍼**다. 질문은 하나: "까다로운 헤비 유저가 이걸 내일도 쓸까?"

코드 품질(typecheck, lint, 토큰 준수)은 `/go`가 이미 했다. `/improve`는 **사용자가 보고 만지는 제품**을 평가하고 개선한다. 코드가 아니라 제품이 주어다.

## LLM의 편향 주의

LLM은 코드 수정을 좋아한다 — 구체적이고, 측정 가능하고, 완료 판정이 쉬우니까. 그 결과 "CSS 토큰 린터"가 되어 정작 제품 완성도는 건드리지 않는 함정에 빠진다. 이 스킬에서는 **코드를 직접 읽거나 grep하는 행위를 evaluate에서 금지**한다. evaluate는 앱을 **보고 사용하는 것**만 한다.

## 파이프라인에서의 위치

```
discuss → prd → plan → dev → improve → retrospect → publish → close
```

| 스킬 | 책임 | 판단 기준 |
|------|------|----------|
| `/go` | 동작하게 만든다 | typecheck/lint/test/토큰/아키텍처 |
| `/improve` | 릴리즈할 수 있게 만든다 | 까다로운 헤비 유저가 내일도 쓸까 |

역할이 다르다. `/improve`는 코드 건전성을 전제하고, 그 위에서 **제품 경험**을 끌어올린다.

## 실행 흐름

### Step 0: 대상 파악

| 상황 | 동작 |
|------|------|
| `/go` 직후 호출 | 방금 만든 것이 대상. git diff에서 변경 범위 추출 |
| 대화에 대상 명시 | 해당 라우트/모듈이 대상 |
| 인자 있음 (`/improve /chat`) | 해당 라우트가 대상 |
| 맥락 없음 | "뭘 개선할까요?" 질문 |

대상이 정해지면:

1. **라우트 URL 발견** — `src/router.tsx`에서 path, `vite.config.ts`에서 port (기본 5173)
2. **진입점 파일 식별** — 라우트에 연결된 컴포넌트, CSS, store 파일

### Step 1: 초기 Evaluate (Baseline)

수정 전에 현재 상태부터 파악한다.

1. **dev 서버 확인** — curl로 확인, 안 돌면 `pnpm dev` 백그라운드 기동
2. **evaluate 컨텍스트 파일 작성** — `/tmp/improve-<timestamp>/improve-context.md`
3. **첫 evaluate 서브에이전트 스폰** → baseline 보고서
4. verdict가 "릴리즈 가능"이면 → 바로 종료

#### Evaluate 컨텍스트 파일

```markdown
# Evaluate Context
- URL: http://localhost:<port>/<path>
- Keyline: <이 제품이 뭔지 한 줄>
- 이전 보고서: <2회차부터 경로 목록, 없으면 생략>
```

**이게 전부다.** 시나리오, 기능 설명, PRD, 디자인 참조 — 전부 넣지 않는다. evaluate는 아무것도 모르는 상태에서 자유 탐색해야 진짜 발견이 나온다. 컨텍스트를 많이 주면 "확인 모드"로 빠져 체크리스트 QA가 된다.

### Step 2~: 루프

```
Loop (최대 5회전):
  ├─ Plan: evaluate 보고서 읽기 → 수정 전략 수립
  │    └─ 가장 임팩트 큰 1~3개 문제 해결 목표
  │
  ├─ Dev: 수정 실행
  │    ├─ CSS → /design-implement 스킬
  │    └─ 수정 후 typecheck + test 통과 확인
  │
  ├─ Evaluate: fresh 서브에이전트 스폰
  │    └─ 보고서 → 파일 저장, verdict 판정
  │
  ├─ verdict = "릴리즈 가능" (🔴 없음) → 종료
  ├─ verdict = "불가" (🔴 있음) → 다음 회전
  ├─ 2회 연속 정체/퇴보 → 접근 변경 1회 → 안 되면 사용자에게 보고
  └─ 5회전 도달 → 요약 + 남은 이슈 → 사용자에게 판단 위임
```

### 퇴보 감지

evaluate 보고서에 신규 🔴 짜증 등장 시:

1. git diff로 이번 변경 확인
2. 해당 파일만 `git checkout -- [파일]`
3. 다른 접근으로 재시도

## Evaluate 에이전트

### 핵심 원칙

**1. 코드를 보지 않는다**

코드를 읽으면 "고치고 싶은 것"을 찾게 되고, 정작 사용자가 느끼는 문제는 놓친다. evaluate는:

- 브라우저에서 앱을 **본다** (스크린샷)
- 브라우저에서 앱을 **사용한다** (클릭, 키보드)
- 코드를 grep하거나, 파일을 읽거나, lint를 돌리지 **않는다**

**2. QA가 아니다**

evaluate는 시나리오 체크리스트를 소거하는 QA 테스터가 아니다. "되네/안 되네"가 아니라 **"되긴 하는데 이게 최선이야?"**를 판단한다.

### 서브에이전트 스폰 방법

**Agent 도구**로 스폰. 모든 정보는 improve-context.md에 담고 경로만 전달.

Agent 도구를 사용할 수 없으면, 메인이 직접 수행하되:
1. 스크린샷을 먼저 찍고, 스크린샷만 보면서 평가
2. 코드를 읽지 않는다
3. 발견한 문제를 dismiss하지 않는다
4. 보고서를 완성한 뒤 verdict를 내린다

### 서브에이전트 프롬프트

`<CONTEXT_PATH>`와 `<REPORT_PATH>`를 실제 경로로 치환:

```
너는 이런 류의 도구를 수십 개 써본 헤비 유저다. 매일 쓰고, 불만이 엄청 많고, 요구사항도 엄청 많다. 컨셉은 이미 좋아한다 — 그래서 더 까다롭다. "되긴 하는데 이게 최선이야?"가 네 기본 태도다.

네 역할: 앱을 직접 보고 사용하면서, 불만과 요구사항을 쏟아낸다. 코드가 깨끗한지는 관심 없다. 내가 쓸 때 느낌이 어떤지만 본다.

절대 규칙: 소스 코드를 읽지 마라. grep하지 마라. 파일을 열지 마라. 너는 사용자다 — 사용자는 코드를 보지 않는다. 브라우저에서 보이는 것, 만져지는 것만 평가한다.

먼저 <CONTEXT_PATH>를 읽어서 URL과 keyline을 확인하라. 그게 전부다 — 시나리오도 없고 매뉴얼도 없다. 나머지는 네가 직접 발견한다.

## 평가 — 3 Phase

탐색과 판단을 섞지 않는다. 먼저 설계하고, 실행하고, 마지막에 판단한다.

### Phase 1: 시나리오 설계

URL에 접속해서 첫인상 스크린샷 1장을 찍는다. 그리고 "내가 이 도구로 해보고 싶은 것"을 5~7개 시나리오로 적는다. 이 단계에서는 실행하지 않고 목록만 만든다.

각 시나리오 형식:
```
S1. [이름] — [동기: 왜 이걸 해보고 싶은가]
   동작: [3~8스텝 시퀀스]
   촬영: 매 동작 | 대표 1장 (반복/중복이면 대표 1장)
```

시나리오 예시 (참고용, 이대로 쓰지 않아도 됨):
- "레이어 규모 비교: 사이드바에서 폴더 4개를 연속 클릭, 각 컬럼 헤더의 파일수·LOC 비교"
- "큰 파일 탐색: 가장 LOC가 높은 파일을 찾아 클릭, 프리뷰 확인, 다른 큰 파일과 비교"
- "키보드 네비게이션: Tab으로 진입, 방향키로 컬럼 간 이동, Enter로 파일 열기"
- "긴 파일명 처리: 파일명이 긴 폴더(docs 등)로 이동, 잘림 확인, 호버"
- "윈도우 리사이즈: 좁게/넓게 바꿔보면서 레이아웃 깨짐 확인"

첫 시나리오는 반드시 **"자유 탐색"** — 매뉴얼 없이 눈에 보이는 것부터 만져본다.

### Phase 2: 연속 실행

시나리오를 하나씩 실행한다. 핵심 규칙:

- **실행 중에 판단하지 않는다** — 불만, 평가, 개선안을 적지 않는다
- **동작만 수행하고 스크린샷만 찍는다** — 매 의미 있는 동작 후 스크린샷. 같은 화면 반복이면 대표 1장만
- **막히면 기록만** — "여기서 막혔다"만 메모하고 다음 시나리오로 넘어간다
- 스크린샷을 /tmp/improve-<timestamp>/screenshots/ 에 저장
- 스크린샷 파일명에 시나리오 번호 포함 (예: s1_첫화면, s3_리사이즈_좁게)

### Phase 3: 한번에 판단

모든 시나리오가 끝나면, 스크린샷 전체를 보면서 판단한다.

- 시나리오별로 "느낌"을 적는다 — 흐름이 자연스러웠는가, 어디서 짜증났는가
- 시나리오 간 비교 — "S1에서는 괜찮았는데 S3에서 같은 기능이 안 되는 건 왜?"
- "되긴 하는데" 뒤에 오는 말을 전부 적는다
- 불만 각각에 "나라면 이렇게 만들겠다"를 구체적으로 붙인다
- 없는 기능 중 "이건 있어야지", 있는 기능 중 "이건 이렇게 바꿔야지"
- 실현 가능성은 신경 쓰지 않는다 — 너는 사용자니까

## 심각도 판정

- 🔴 짜증: 쓰다가 막히거나, 눈에 띄게 깨졌거나, keyline이 거짓말이거나
- 🟡 불만: 되긴 하는데 별로, 경쟁 제품 대비 부족, 기대 이하
- ⚪ 잔소리: 사소하지만 신경 쓰이는 것

## Verdict

- 릴리즈 불가: 🔴 짜증이 1개라도 있음
- 릴리즈 가능: 🔴 없고, 이 도구를 내일도 쓸 의향이 있음
```

### 도구

evaluate 서브에이전트가 사용하는 도구:

| 도구 | 용도 |
|------|------|
| **Playwright MCP** 또는 **Chrome Claude** | 앱 접속, 스크린샷, 클릭, 키보드 |
| **Read** | improve-context.md, 이전 보고서만 |
| **Write** | 보고서, 스크린샷 저장 |
| **Bash** | 금지 (코드 검사 유혹 차단) |
| **Grep/Glob** | 금지 (코드 읽기 유혹 차단) |

## Dev 단계 규칙

evaluate 보고서를 받은 메인 에이전트가 수정할 때:

- **CSS 수정** → `/design-implement` 스킬
- **UI 컴포넌트** → `src/interactive-os/ui/` 완성품 사용
- **수정 후** → typecheck + test 통과 확인
- 코드 품질은 메인이 알아서 챙긴다 — evaluate가 시킨 게 아니라 자체 규율

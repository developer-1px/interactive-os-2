### 공통 원인

P1, P3, P4가 동시에 존재하는 이유: **칸반 컬럼의 배치가 파일시스템 구조(폴더명 알파벳순)를 그대로 반영할 뿐, 코드의 의미적 관계(의존 방향)를 반영하지 않는다.** 의존 정보는 이미 서버에서 제공하고 있지만(depCounts, imports API), 이 정보가 레이아웃 자체에 반영되지 않고 개별 카드의 하이라이트/숫자로만 사용된다.

P2, P7, P8이 동시에 존재하는 이유: **파일의 중요도(참조 빈도)와 크기(LOC)가 숫자 텍스트로만 표현되고, 레이아웃/시각 비중에 반영되지 않는다.** 칸반 카드가 균일한 크기라서 "조망"이 아니라 "목록 읽기"가 된다.

### Feature 1: Import-Graph Topological Column Ordering

**컬럼을 import 그래프의 위상 정렬 순서로 자동 배치한다.**

- 이 feature가 해결하는 Pain: P1, P4
- 제품이 어떻게 바뀌는가: "파일 이름 나열" → "의존 흐름 시각화". 좌측 컬럼의 파일이 우측 컬럼의 파일을 import하는 흐름이 자명해진다.
- 사용자의 행동이 어떻게 바뀌는가: 아키텍처 레이어 순서를 머릿속에 기억할 필요가 없다. 칸반을 왼쪽에서 오른쪽으로 읽으면 자연스럽게 "기반 → 소비자" 흐름이 보인다. 하이라이트의 방향도 좌/우로 분명해진다.
- **보편성**: 이 feature는 import/require 문이 있는 모든 JS/TS/Python/Go 프로젝트에서 작동한다. 이유: 의존 순서를 `_meta.yaml`이나 `CLAUDE.md`에서 읽는 것이 아니라, 이미 서버가 제공하는 파일 간 import 관계(`/api/fs/imports`)에서 위상 정렬을 자동 계산한다. 프로젝트별 설정이 필요 없다.

#### 변경

- `birdseyeTransform.ts`: `buildKanbanStore`에서 `sortDirs()` 호출 시, `columnOrder` 옵션이 없으면 depCounts 기반 위상 정렬 결과를 사용
- `BirdseyeLayout.tsx`: `_meta.yaml` 없는 경우 서버의 depCounts에서 폴더 간 의존 방향을 집계하여 정렬 순서 계산
- 서버 측: 기존 `/api/fs/imports` 응답에 이미 충분한 데이터 존재. 폴더 단위로 집계하는 로직만 클라이언트에 추가.

#### 검증

- `_meta.yaml`이 없는 폴더에서 컬럼 순서가 "기반 레이어 → 소비 레이어" 순으로 표시되는지 확인
- 기존 `_meta.yaml`이 있는 폴더는 여전히 수동 순서를 우선 사용

### Feature 2: Treemap Zoom-Out Mode

**줌아웃 토글로 카드를 LOC 비례 사각형 블록으로 압축하여 폴더 전체를 한 화면에 표시한다.**

- 이 feature가 해결하는 Pain: P2, P3, P7
- 제품이 어떻게 바뀌는가: "목록 읽기" → "지도 조망". 한 화면에서 폴더 내 모든 파일의 상대적 크기와 분포를 즉시 파악할 수 있다.
- 사용자의 행동이 어떻게 바뀌는가: 가로 스크롤 없이 전체 구조를 본 뒤, 관심 영역을 클릭하여 줌인. 큰 파일과 작은 파일의 비율이 면적으로 자명하여 숫자를 읽을 필요가 없다.
- **보편성**: 이 feature는 LOC 정보가 있는 모든 코드베이스에서 작동한다. 이유: treemap 레이아웃은 (이름, 크기) 쌍만 있으면 동작하는 범용 시각화. LOC는 이미 서버 응답에 포함되어 있으므로 추가 설정 불필요.

#### 변경

- `BirdseyeLayout.tsx`: 헤더에 줌 토글 버튼 추가 (kanban / treemap)
- 새 컴포넌트 또는 `Kanban` variant: treemap 레이아웃 렌더링 (squarified treemap 알고리즘)
- `BirdseyeLayout.module.css`: treemap 블록 스타일 (면적 비례, ext 색상 유지)

#### 검증

- 줌아웃 모드에서 가로 스크롤 없이 폴더 전체가 한 화면에 표시되는지 확인
- 가장 큰 파일이 가장 큰 블록으로 표시되는지 확인
- 블록 클릭 시 줌인(카드 포커스)으로 전환되는지 확인

### Feature 3: QuickOpen-to-Kanban Navigation Bridge

**QuickOpen에서 파일 선택 시 해당 파일이 속한 폴더로 칸반을 자동 이동하고 카드를 포커스한다.**

- 이 feature가 해결하는 Pain: P9, P5
- 제품이 어떻게 바뀌는가: QuickOpen이 "코드 미리보기 도구"에서 "구조 내 위치 탐색기"로 확장된다.
- 사용자의 행동이 어떻게 바뀌는가: 파일명으로 검색 → 선택 → 칸반에서 해당 파일의 구조적 위치(어떤 폴더, 어떤 이웃 파일)를 즉시 확인. 의존 하이라이트도 자동 활성화.
- **보편성**: 이 feature는 파일 시스템 트리가 있는 모든 프로젝트에서 작동한다. 이유: 파일 경로에서 부모 폴더를 추출하는 것은 범용 연산.

#### 변경

- `BirdseyeLayout.tsx`: `handleQuickOpenSelect` 수정 — 파일 경로에서 부모 폴더 추출 → `selectFolder(parentDir)` → 칸반 렌더 후 해당 카드 DOM 포커스
- 기존 `handleDepJump`의 "다른 폴더의 파일" 로직과 유사하게 구현

#### 검증

- QuickOpen에서 다른 폴더의 파일을 선택하면 칸반이 해당 폴더로 이동하는지 확인
- 이동 후 해당 카드가 포커스되고 의존 하이라이트가 활성화되는지 확인

1. **Feature 3 (QuickOpen Bridge)** — 가장 작은 변경량으로 가장 즉각적인 가치. 기존 코드 패턴(`handleDepJump`) 재사용 가능.

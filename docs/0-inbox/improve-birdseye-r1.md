# Pain→Wow 제안서 — Birdseye Round 1

## Pain 목록

### P1. 레이어 간 의존 관계가 안 보인다
- **어디서**: 각 열(column) 사이의 공간
- **상황**: 사용자가 "axis가 정말 pattern을 알고 있나?", "이 파일이 실제로 위 레이어를 쓰고 있나?" 궁금할 때
- **왜 아픈지**: Keyline은 "아키텍처 레이어 순서"인데, 순서만 있고 관계(의존성)는 없다. 각 파일이 위/아래 레이어의 어떤 것을 쓰는지 알 수 없어서, 정말 계층 구조가 지켜지고 있는지 신뢰할 수 없다.

→ **Wow: 파일 위에 마우스를 올리면 (또는 클릭하면) 그 파일이 의존하는 위 레이어의 파일들과 자신을 의존하는 아래 레이어의 파일들이 시각적으로 강조된다.**

이렇게 되면:
- 사용자는 한눈에 "pattern은 axis의 navigate, select, expand, activate 등을 정말 쓰고 있네" 확인 가능
- 역으로 "engine은 어떤 plugin들이 나를 의존하나" 추적 가능
- 아키텍처 규칙 위반(하향 의존)을 시각적으로 탐지 가능
- 새 개발자가 "이 파일 써도 되나?" 빠르게 판단 가능

---

### P2. 파일 크기의 의미가 모호하다
- **어디서**: 각 파일 옆의 바이트 수 (e.g., "135L +24 +5")
- **상황**: 사용자가 "135L이 크면 작은 거야? 뭘 기준으로 판단하지?" 할 때
- **왜 아픈지**: 숫자는 있는데 맥락이 없다. 같은 레이어 내 평균 대비 어느 정도인지, 역사적으로 증가/감소 추세인지, 허용 범위를 넘었는지 알 수 없다. 단순 수치만으로는 "지금 코드가 건강한가"를 판단할 수 없다.

→ **Wow: 파일 크기가 색상 그래디언트로 표현되고, 열 헤더에 "평균: 68L, 경고: 200L+" 같은 레이어별 가이드라인이 보인다. 급증한 파일(작년 대비 +40%) 옆에 ⚠️ 마크가 붙는다.**

이렇게 되면:
- 사용자는 한눈에 "이 레이어는 전체적으로 균형 잡혀 있구나" 또는 "Pattern 파일 하나가 비정상으로 커졌네" 인식
- 복잡도 증가를 조기 경보로 감지 (리팩토링 신호)
- 새 파일 추가 시 "이 크기가 건강한 수준인가" 의식적으로 검토

---

### P3. 레이어 내 파일들의 역할 분류가 없다
- **어디서**: 예를 들어 axis 열에 "activate.ts", "navigate.ts", "checked.ts" 등 섞여 있음
- **상황**: 사용자가 "axis 안에 몇 개의 축이 있고, 각각 얼마나 복잡한가?"를 파악하고 싶을 때
- **왜 아픈지**: 파일은 나열되지만, 각 파일이 어떤 역할(core axis vs utility vs adapter)인지, 어느 파일이 "메인 비즈니스 로직"이고 어느 파일이 "지원"인지 구분이 안 된다. 구조화 없이 나열만 있다.

→ **Wow: 각 레이어 열 내부가 3~4개의 시각적 그룹(sections)으로 나뉜다. 예: Axis는 "Core 축(navigate, select…)", "View 상태(checked, disabled…)", "Plugin 통합" 섹션으로 구분되고, 섹션별로 약간씩 다른 배경색이나 구분선이 있다. 섹션 헤더에 "Core Axes (5)" 같은 라벨이 붙는다.**

이렇게 되면:
- 새 개발자가 "여기 어디에 새 축을 추가해야 하나?" 한눈에 이해
- 각 섹션의 역할이 명확해서 파일 설계 시 "이 로직은 누구 책임인가" 빠르게 결정
- 리팩토링 필요성 시 "이 섹션이 살찌고 있다" 정량적으로 감지
- Keyline("레이어 순서")이 "레이어 + 역할"로 진화

---

### P4. 전체 크기와 성장 속도 추이가 안 보인다
- **어디서**: 오른쪽 끝 "metrics" 같은 영역 (현재는 보이지 않음)
- **상황**: 사용자가 "이 프로젝트가 월별로 얼마나 복잡해지고 있나?", "최근 3개월 중 가장 큰 변화는?" 알고 싶을 때
- **왜 아픈지**: 현재는 "지금 이 순간"의 스냅샷만 보인다. 레이어별 크기 추이, 성장률, 변동 패턴이 없어서 "장기적으로 건강한가" 판단 불가. 무한정 커질 수도 있고, 리팩토링의 효과를 수치로 증명할 수도 없다.

→ **Wow: 각 레이어 헤더 옆에 작은 미니 차트(sparkline)가 있어서 최근 10개 커밋에서의 크기 변화 추이가 선 그래프로 보인다. 헤더를 클릭하면 모달에서 "Axis: 최근 90일 추이, 주당 +2% 성장" 같은 상세 지표가 나타난다.**

이렇게 되면:
- 사용자는 "axis가 커지고 있구나" 또는 "리팩토링으로 30% 줄었네" 한눈에 인식
- 팀 회의에서 "최근 기술부채 증가 추세가 보이니 리팩토링 스프린트 필요" 데이터 기반 논증 가능
- 각 레이어의 건강도를 "score:design" 같은 자동화 도구와 연결 → 회귀 조기 경보

---

### P5. Pages 폴더 구조와 interactive-os의 계층이 분리되어 보인다
- **어디서**: 두 번째 탭 (pages) — 7개 열이 뜸
- **상황**: 사용자가 "pages의 각 폴더(viewer, cms, etc.)가 interactive-os의 어느 레이어를 쓰나?" 궁금할 때
- **왜 아픈지**: 두 개의 분리된 탭으로 나뉘어 있어서, 전체 아키텍처 맥락에서 "pages → interactive-os → engine…" 의존 흐름이 단절되어 보인다. Pages가 interactive-os의 위에 있다는 것을 시각적으로 표현하지 않는다.

→ **Wow: Pages를 두 번째 탭이 아니라 interactive-os 위(상단)에 하나의 열로 추가하되, 시각적으로 경계를 명확히 한다 (예: 밝은 배경 vs 어두운 배경). 또는 토글로 "전체 뷰" vs "interactive-os만" vs "pages만" 전환 가능하게 해서, 기본은 "전체 뷰"로 레이어 순서를 직관적으로 보여준다.**

이렇게 되면:
- Keyline("레이어 순서")가 물리적으로 위→아래 순서로 시각화
- 새 개발자가 "pages는 최상위, interactive-os는 다음, engine은 그 아래" 즉시 이해
- Pages 내 각 폴더가 interactive-os의 어떤 부분을 쓰는지 화면 한 번에 추적 가능

---

## 가장 임팩트 큰 Wow 3개

1. **P1 + P3 결합: 의존성 + 역할 분류 시각화** — "한 파일을 보면 누가 나를 쓰고, 내가 뭘 쓰고, 내 역할이 뭔지" 한눈에. 아키텍처 신뢰도 극대화 + 설계 시간 단축 (신규 입사자 온보딩 50% 가속)

2. **P2 + P4 결합: 파일 크기 → 건강도 신호로** — 색상 + 추이 차트로 "이 레이어가 비정상으로 커지고 있나" 자동 감지. 기술부채 조기 경보 시스템 확보 (리팩토링 우선순위 객관화)

3. **P5: 전체 계층 맥락화** — Pages부터 시작하는 상향식 전체 뷰로 "우리 시스템이 어떻게 위아래로 쌓여 있나" 한눈에 이해. 신규 기능 추가 시 "어느 레이어에서 시작해야 하나" 즉시 판단 (아키텍처 규칙 위반 사전 차단)

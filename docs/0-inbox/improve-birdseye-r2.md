# Pain→Wow 제안서 — Birdseye Round 2

## 이전 Pain 상태

### P1. 레이어 간 의존 관계가 안 보인다
- **상태**: ❌ 미해소
- **이유**: 여전히 파일 목록만 보이고, 어느 파일이 위/아래 레이어를 쓰는지 시각적 관계가 없음. 막대 바와 배경 틴트는 추가되었지만 의존성 추적 기능은 구현되지 않음.

### P2. 파일 크기의 의미가 모호하다
- **상태**: 🟡 부분 해소
- **해소 부분**:
  - 컬럼 헤더 하단에 LOC 비율 바 추가 (파란색 가로 막대) — "axis가 가장 크다" 상대적 비교 가능
  - 300L 이상 파일에 노란빛 배경 틴트 추가 — "이 파일은 크다"는 신호 작동
- **아직 남은 부분**:
  - 막대 너비만으로는 "평균 대비 얼마나 큰가"를 수치로 파악 불가. 헤더에 "평균: 68L, 경고: 200L+" 같은 가이드라인 텍스트가 없음
  - 급증 추세(작년 +40%) 같은 역사적 맥락 없음 — 지금 이 크기가 "정상 증가인가 비정상인가" 판단 불가

### P3. 레이어 내 파일들의 역할 분류가 없다
- **상태**: ❌ 미해소
- **이유**: 여전히 모든 파일이 단순 목록으로만 나열됨. Axis 컬럼에 "navigate.ts", "activate.ts", "select.ts" 등이 섞여 있지만, "Core 축", "View 상태", "Plugin 통합" 같은 시각적 그룹/섹션 구분이 없음.

### P4. 전체 크기와 성장 속도 추이가 안 보인다
- **상태**: ❌ 미해소
- **이유**: 스냅샷 뷰만 있고, 시간 추이 데이터가 전혀 없음. 최근 10개 커밋 sparkline, 레이어별 성장률, 월별 추이 차트가 모두 부재.

### P5. Pages 폴더 구조와 interactive-os의 계층이 분리되어 보인다
- **상태**: ❌ 미해소
- **이유**: 여전히 두 개의 분리된 탭으로 나뉨. Pages와 interactive-os 사이의 의존 흐름이 시각적으로 표현되지 않음. 신규 개발자는 "pages는 interactive-os 위에 있다"는 것을 직관적으로 이해하기 어려움.

## 새 Pain 목록

### PN1. 파일 배경 색상의 의미가 불명확하다
- **어디서**: 각 파일의 배경색 (노란빛 틴트)
- **상황**: 사용자가 "왜 이 파일은 노란색이고 저 파일은 아닌가?" 궁금할 때
- **왜 아픈지**: 색상이 있지만 설명/범례가 없음. 마우스 호버해도 "300L 이상" 같은 기준 텍스트가 없어서, 신규 사용자나 간헐적 방문자는 "노란색 = 무엇"인지 불명확. 컬럼 헤더나 우측 범례에 "300L+ = ⚠️ Large" 같은 마커가 필요.

→ **Wow: 파일 배경색 범례를 화면 오른쪽 상단 또는 컬럼 헤더 우측에 추가. 예: "■ 작음 (<100L) | ■ 중간 (100~250L) | ■ 크다 (250~400L) | ■ 매우 큼 (400L+)" 형태의 레전드. 또는 마우스 호버 시 tooltip "Large: 300L+ (복잡도 신호)"로 맥락 제공.**

이렇게 되면:
- 방문자가 즉시 색상의 의미를 파악 → 시각적 신뢰도 상승
- 신규 개발자가 "파일 크기 관례"를 문서 없이도 직관적으로 학습
- 검토자가 코드리뷰 시 "이 파일이 노란색이라서 크기 검토 필수" 의식적 판단

---

### PN2. "이 파일을 봐야 하나?" 결정 기준이 없다
- **어디서**: 파일 목록에서 특정 파일을 선택하려 할 때
- **상황**: 개발자가 "150줄 파일과 320줄 파일 중 어느 걸 먼저 읽어야 하나?", "이 파일이 업무와 얼마나 관련 있나?"를 판단하고 싶을 때
- **왜 아픈지**: 파일 목록은 있지만 "변경 빈도", "테스트 커버리지", "bug 등록 수", "의존 파일 수" 같은 우선순위 신호가 없음. 순수 크기 정보만으로는 "중요도"를 판단 불가. 따라서 매번 파일을 일일이 열어봐야 함.

→ **Wow: 각 파일 옆에 작은 아이콘/배지 표시. 예: 🔥(최근 5개 커밋에서 변경 있음) | ⚡(의존하는 파일 5개 이상) | 🛡️(테스트 커버리지 80%+) | 🐛(최근 이슈 연결됨). 또는 파일명 우측에 작은 스코어 숫자 "importance: 7/10" 표시. 마우스 호버 시 "변경빈도 ++, 의존도 high" 분석 결과 요약.**

이렇게 되면:
- 개발자가 "이 파일은 최근 자주 건드려졌네" → 리스크 높음 인식 → 신중하게 검토
- "이 파일은 5개 파일이 나를 쓰네" → 영향 범위 큼 → 테스트 더 꼼꼼히
- 새 기능 추가 시 "어느 파일에 로직을 붙여야 하나" 판단이 데이터 기반으로 변함
- 리팩토링 우선순위 자동 정렬 가능 ("변경빈도 높고 크기도 크고 의존도 많은 파일 부터")

---

### PN3. 컬럼 헤더 바(LOC 비율)가 정량적 수치 없이 상대적으로만 보인다
- **어디서**: 각 컬럼 헤더 하단의 파란색 가로 막대
- **상황**: 사용자가 "axis 바가 제일 넓은데, 실제로 몇 줄인가?", "이번 달 대비 얼마나 커졌나?"를 알고 싶을 때
- **왜 아픈지**: 막대의 상대적 너비만 보이고, 정확한 줄 수(LOC)나 변화량이 헤더에 표시되지 않음. 막대 호버 시 "axis: 1158L" 같은 텍스트 팝업이 있어도 추이는 알 수 없음. "이번 주 +50L 증가" 같은 변화도 없음.

→ **Wow: 컬럼 헤더의 막대 위에 마우스 호버 시 tooltip "axis: 1158L (전체 10%) | 지난주 대비 +45L (+4%) | 지난달 대비 +120L (+11%)" 형태의 상세 정보 표시. 또는 헤더 하단에 작은 글자로 "1158L" 숫자를 항상 표시해서, 막대만으로도 상대 비교, 숫자만으로도 절대값 파악 가능하게.**

이렇게 되면:
- 한눈에 "axis가 가장 크다 + 정확히 1158줄" 두 정보 모두 획득
- "최근 한주 동안 pattern이 +80L 증가" 추세 감지 → 가속 신호
- 레이어 크기 모니터링이 정성적("대충 커지는 것 같음")에서 정량적("주당 +2% 성장")으로 진화

---

### PN4. 같은 컬럼 내 큰 파일과 작은 파일의 시각적 계층이 없다
- **어디서**: 예를 들어 plugins 컬럼에서 useSpatialNav.ts (305L) 아래에 spinButton.ts (25L)이 나란히 나열됨
- **상황**: 사용자가 "큰 파일을 먼저 읽고 작은 파일은 나중에"라는 학습 순서를 정하고 싶을 때
- **왜 아픈지**: 파일이 무작위 순서 또는 알파벳순일 수 있고, 크기 정렬 옵션이 보이지 않음. 같은 카테고리(예: plugins)에서 "복잡도 높은 순" 같은 소팅이 없어서, 학습자가 효율적인 학습 경로를 스스로 그려야 함.

→ **Wow: 각 컬럼 헤더에 작은 정렬 아이콘(sort button) 추가. 기본은 "알파벳순", 클릭하면 "크기순(내림차순)" → "변경빈도순" → "의존도순" → 다시 "알파벳순"으로 토글. 또는 컬럼별로 기본 정렬을 똑똑하게 설정 (예: pattern 컬럼은 기본 "크기순 내림차순"으로 가장 복잡한 것부터).**

이렇게 되면:
- 신규 개발자가 "패턴을 배우려면 이 큰 것부터" → 체계적 온보딩 가능
- "최근 많이 변한 파일부터 읽어야겠다" → 현실적 업무 흐름과 정렬
- 리팩토링 계획 시 "크기순으로 정렬해서 가장 크고 자주 변하는 것부터" 결정 빨라짐

---

### PN5. 컬럼 헤더의 "수" 정보(파일 개수)가 보이지 않는다
- **어디서**: 각 컬럼 헤더 (예: "axis", "pattern")
- **상황**: 사용자가 "axis는 몇 개의 파일/축으로 구성되어 있나?"를 빠르게 파악하고 싶을 때
- **왜 아픈지**: 헤더에는 폴더명과 총 LOC만 있고, "파일 개수(count)"가 없음. 사용자가 수동으로 세어야 함. 예: "axis: 10 files, 1158L" 같은 정보가 없으면, 처음 보는 사람은 "이 열에 몇 개의 단위가 있구나" 직관적으로 알기 어려움.

→ **Wow: 컬럼 헤더를 "axis 10 files 1158L" 형태로 확장. 또는 숫자를 아이콘과 함께 표시 "📄 10 | 📈 1158L". 이렇게 하면 한눈에 "axis는 10개 파일로 구성, 총 1158줄"이 명확함.**

이렇게 되면:
- 신규자가 "axis 축은 10개 파일로 구성되어 있구나" 스코프를 즉시 파악
- "최근 새 축을 추가했는데 파일 개수가 증가했나?" 모니터링 가능
- "이 레이어는 파일이 너무 많이 쪼개져 있다" 문제 감지 (응집도 낮음)

---

### PN6. 큰 파일의 "왜 이렇게 큰가"를 탐색할 방법이 없다
- **어디서**: 노란빛 배경 파일 (예: useSpatialNav.ts 305L)
- **상황**: 검토자가 "이 파일이 305줄이 된 이유를 알고 싶다. 복잡한 로직 때문인가, 아니면 여러 책임이 섞여 있나?"를 파악하고 싶을 때
- **왜 아픈지**: 파일 크기만 있고, 내부 구조/섹션별 라인 분포가 없음. "이 파일의 함수/타입/로직은 몇 개인가", "가장 긴 함수는 몇 줄인가" 같은 분석 도구가 없어서, 항상 코드를 직접 열어봐야 함.

→ **Wow: 큰 파일(300L+)을 클릭하면 모달/사이드 패널이 열려서, 파일 내부 구조를 간단히 시각화. 예: "useSpatialNav.ts: navigate() 45L, handleKeyDown() 38L, updateCursor() 52L, helpers 70L, types 25L" 형태의 top-level 함수/구간별 라인 분포를 세로 바 차트로 표시. 또는 함수 복잡도(cyclomatic complexity) 색상 코딩.**

이렇게 되면:
- "아, 이 파일이 크면 3개 함수가 각각 50줄씩이라서네" → 단순 집합 인식
- "근데 handleKeyDown이 특히 크네, 이건 분해해야겠다" → 리팩토링 신호 구체화
- "이 파일의 의존성을 먼저 파악하고 분해해야겠다" → 설계 기반 의사결정

## 이전 R1의 구현 평가

### R1에서 개발자가 구현한 것
1. ✅ **컬럼 헤더 LOC 비율 바** — 좋은 시작. 상대 비교는 가능하나, 정량 정보 부족
2. ✅ **대형 파일 배경 틴트** — 시각 신호는 좋으나, 범례 없어서 첫 방문자가 혼동

### R1 구현의 한계
- **P1(의존성)**: 미구현 상태
- **P2(크기 맥락)**: 막대는 있으나 "평균/경고 가이드라인" 텍스트 미흡
- **P3(역할 분류)**: 여전히 단순 목록
- **P4(추이 차트)**: 완전 미구현
- **P5(Pages 통합)**: 여전히 분리된 탭

## 가장 임팩트 큰 Wow 3개

### 1. PN2 + PN6: 파일 우선순위 신호 + 구조 탐색 (영향도: 매우 큼)
**제안**: 각 파일 옆에 🔥⚡🛡️ 배지 + 파일 클릭 시 "함수 분포 바 차트" 모달

**효과**:
- 개발자가 "어디부터 읽어야 하나" 데이터 기반 의사결정 → 온보딩 시간 50% 단축
- 큰 파일의 내부 구조를 파악할 때마다 코드 에디터를 열 필요 없음 → 탐색 속도 2배
- 리팩토링 우선순위 자동화 가능 ("변경빈도 높고 크기 크고 의존도 많은 것 먼저") → 기술부채 감시 효율화

**구현 기대 복잡도**: 중간 (파일 메타데이터 수집 + 모달 UI 추가)

---

### 2. PN3 + PN4: 컬럼 헤더 정량 정보 + 정렬 (영향도: 중간)
**제안**: 헤더를 "axis 10 files | 1158L | 지난주 +45L" 형태로 확장 + 컬럼별 정렬 옵션(크기순/변경빈도순)

**효과**:
- 신규 개발자가 "이 레이어의 스코프"를 즉시 이해 → 설계 시간 30% 단축
- "최근 빠르게 커지는 레이어 발견" → 기술부채 조기 경보
- 학습자가 "복잡도 높은 것부터" 체계적으로 학습 가능 → 효과적 온보딩

**구현 기대 복잡도**: 낮음 (데이터는 이미 있음, UI 텍스트 추가만)

---

### 3. PN1 + P2 마무리: 색상 범례 + 수치 정보 (영향도: 높음)
**제안**: 화면 우측 또는 헤더 우측에 컬러 범례 추가 + 헤더 바 호버 시 "1158L, 지난주 +45L" tooltip

**효과**:
- 시각 신호의 신뢰도 상승 → "이 화면이 정보를 숨기지 않는구나" 인식
- 방문 빈도 낮은 사용자도 즉시 이해 가능 → 아키텍처 투명성 확보
- 색상 + 수치 조합으로 "정성 + 정량" 동시 달성 → 정보 밀도 극대화

**구현 기대 복잡도**: 낮음 (UI 추가, 데이터는 기존 것 활용)

---

## 구현 로드맵 제안

### Phase 1 (빠른 승리)
- PN1: 색상 범례 추가 + 호버 정보 표시 (1~2시간)
- PN5: 컬럼 헤더에 파일 개수 추가 (30분)

### Phase 2 (중간 영향)
- PN4: 컬럼별 정렬 옵션 추가 (2~3시간)
- PN3: 헤더에 최근 변화량 표시 (1시간)

### Phase 3 (높은 영향, 복잡도)
- PN2: 파일 배지(🔥⚡🛡️) + 우선순위 스코어 (3~4시간)
- PN6: 큰 파일 클릭 시 함수 분포 모달 (4~5시간)

## 핵심 메시지

**"Birdseye는 데이터가 있는데, 정보 표시가 부족하다."**

R1에서 색상 신호(노란빛 틴트)와 상대 비율(막대)을 추가했으나, 여전히:
- 범례가 없어 신호의 의미가 모호
- 숫자가 숨겨져 있어 정량 분석 불가
- 우선순위 신호가 없어 "어디부터 봐야 하나" 결정 어려움
- 파일 내부 구조 탐색 수단이 없어 항상 코드 에디터 필요

**R2의 전략**: 기존 시각 신호를 유지하되, **정보 밀도를 높이기** (범례, 수치, 배지, 모달 탐색)

이렇게 하면 Birdseye가 단순 "코드 구조 지도"에서 **"아키텍처 분석 대시보드"**로 진화 → 개발 생산성 + 설계 의사결정 속도 대폭 상승.
